# Durable revisions of applied ideas

Implemented locally after saved purchasing supplies. Domain checks are green; browser and packaged qualification are recorded in the current requirements audit.

## Current behavior

Previously, furniture sections retained a typed `Section.recipe`, structures retained no family specification and proposals lived only while the dialog was open. Applying another proposal appended assemblies. The new saved binding records the original application and entry identities so reopening and revising update only the selected design entries.

## Design

- Persist default-empty, versioned `Project.ideaBindings`. Each application has a stable ID/revision, entry IDs, typed furniture/structure specifications, section-role mappings and an entry-local baseline fingerprint. Keep assumptions/questions/suggestions with the application. Validate these using neutral shared schemas, avoiding generator/model import cycles. Do not allocate IDs during parsing.
- Initial Apply creates IDs and records the sections generated by each entry. Furniture maps to one section. Whole-build structures map to multiple stable roles. New Add operations allocate separate entries. Reconstruct an editable proposal from a binding after save/import/reopen.
- Give “Revise existing” an explicit target application/entry. Carry the binding revision and fingerprint with the request. Reject stale replies. Preserve section IDs for surviving roles, unrelated parts/settings/source selections and manually added supply records. New generated pieces get fresh IDs; affected connections are counted and explicitly removed on regeneration; the guide becomes stale.
- Preserve rigid assembly moves, rotations and lid previews without regeneration. Update stored pose when the whole assembly moves. Detect individual cuts, profile/stock-direction/source-lineage edits and member moves in entry-local coordinates. Show the concrete manual-edit/connection impact before a rebuild. Keeping custom work or detaching the binding remains possible; never silently discard custom cuts/offcuts.
- Copies allocate new application/entry IDs. Partial structural copies are independent. Deletion updates mappings. Legacy furniture can explicitly adopt its saved recipe as a baseline without replacing existing custom cuts or connections; regenerated geometry determines its manual-change review. Legacy structures are not inferred from names.

## Implementation notes

- `materialIds.ts`, `recipeSchemas.ts` and `planSchema.ts` separate persisted schemas from generation. `ideaGeometry.ts` owns deterministic generation; `ideaBindings.ts` owns reconstruction, selective revision, impact and stale-token checks. `ideaBindingState.ts` integrates ordinary section edits, copying and deletion. Imported fingerprints never establish geometry approval.
- Unchanged entries retain actual pieces, cuts, provenance and joints. Pose-only changes transform those actual pieces. Dimensional rebuilds replace only affected entries; custom cut members are retained as reusable loose cut parts, alongside existing offcuts. The commit path requires acknowledgement of destructive impacts.
- The idea dialog offers new-design versus saved-design/entry targets. Sections list saved designs and explicit legacy adoption/detachment. Exact placement controls use independent length units; rotations use degrees, counts remain counts. Whole structure families move together without rebuilding parts.
- Current structured assumptions and open decisions appear in guide Markdown and print, while custom notes/history remain. Repeated revisions reuse current step IDs rather than accumulating unused phases. Bundled examples are refreshed with bindings and matching current guides.

## Required checks

Apply → save → reopen → revise without duplicate geometry; whole-run and named-seat changes; multi-section greenhouse revision; unrelated geometry/products/supplies preserved; rotated whole builds; manual cuts/offcuts and connections surfaced before rebuild; copy/delete and undo; stale replies; older JSON; guide regeneration/persistence. Actual model interpretation remains a separate qualification from deterministic replacement and persistence.
